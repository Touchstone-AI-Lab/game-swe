Card authors report that conditional descriptions lose literal text, select the wrong suffix branch, or crash while being initialized. Descriptions supplied by card effects can also remain stale when the card is drawn again after a value changes.

Repair conditional description expansion, including the following intended language behavior. A complete effective description opts in with `{@@}`; remove that marker from its displayed text. Without the marker, the description is literal, even if that card previously opted in. Effects and description subscribers can supply the marker and conditional text; they must work the same way as text written directly on the card.

A block has the form `{!key!|condition=payload|condition=payload}`. Keep the existing variable and registered custom-check sources. Select the rightmost matching condition. Use the last `@` fallback only when no condition matches; an unknown variable expands to empty text. Conditions can be comma-separated alternatives, integer equality, strict `>` or `<`, divisibility with `%`, a decimal suffix with `&`, or `repeat`. Repetition emits the payload max(value, 0) times. Conditions use signed decimal integers in the 32-bit range; malformed numbers and a zero divisor do not match and must not abort expansion. A suffix is a nonnegative digit string matched against the magnitude's decimal trailing digits, including its written leading-zero width; handle the minimum integer without overflow.

Only the first top-level `=` separates a condition from its payload. Subsequent equals signs, dollar signs and ordinary backslashes are literal payload data. A backslash can escape `|`, `{`, `}` or another backslash; leave other backslash sequences unchanged. Support balanced nested blocks inside payloads as part of this repair: only expand the selected payload, and do not evaluate variable callbacks found solely in unused branches. Escaped delimiters stay literal and cannot become a new block or branch during a later expansion pass. Preserve the existing explicit-empty-payload and rightmost-match behavior.

Each initialization or description render uses one coherent value snapshot: repeated references to a key share its first obtained value for that refresh, including references in selected nested payloads. A later initialization or render obtains fresh values. Do not share cached values between separate cards. A custom check may initialize another card while calculating its value; completing that nested initialization must not overwrite the outer card's snapshot.

Actual displayed card descriptions must refresh when values or effect-generated descriptions change. Preserve ordinary non-conditional descriptions, existing card effect/subscriber integration, the normal and character-based description paths, and public extension APIs. No particular parsing, caching, or refresh implementation is required.

The project is in `/app/basemod`. Build offline with `mvn -B -o clean test package -pl mod -am`.
