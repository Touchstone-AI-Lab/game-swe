Players report that custom shields can add up to more block than the creature actually has. Near the block cap, a small later loss can unexpectedly consume a large part of an older shield. A shield-removal request for zero can also change which shield the next ordinary loss affects. Removing a shield whose callback refunds block or removes another shield can throw, notify twice, or leave the displayed block and shield amounts inconsistent.

Repair block accounting for players and monsters. Acquisition must record only the amount actually accepted under the normal 999 block cap, including mixed ordinary and custom block. An acquisition that adds zero must not create an empty layer. Preserve previously existing layers and ordinary stacking and priority behavior.

An explicit block loss must debit the layers that existed for that operation in their normal priority order, or the requested layer for a targeted removal. Block created by a removal callback is a subsequent gain and must not be consumed retroactively by the triggering loss. Finite nested ordinary or targeted removal, including removal on another creature, must complete independently and leave native block equal to the sum of the surviving layers. Notify a layer's modifiers exactly once when that operation exhausts the layer, preserving the remaining-loss argument. Zero and already-empty targeted removals must be harmless and must not influence a later loss.

Preserve public APIs, ordinary partial/complete losses, attack damage and existing removal-based damage reduction. No particular storage, callback scheduling or reconciliation design is required. The project is in `/app/stslib`. Build offline with `mvn -B -o clean test package`.
