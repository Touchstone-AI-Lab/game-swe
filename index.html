    WHY A LIVE RUNTIME

    Repository tests pass.
    The game still breaks.

    Coding agents are usually graded by a repository's own tests. Much software runs inside a host program instead, where correctness depends on runtime state, lifecycle events and third-party code loaded beside it. GameSWE checks agents' code in that setting, inside the shipped game or its dedicated server.

    01

    The game is the judge

    The verdict comes from the running game, not from mocks, model-written tests or LLM judges. A mod that calls an interface the game does not expose fails the way it would for players.

    02

    Stateful, with a lifecycle

    Tests drive the game's lifecycle. A reloaded Minecraft config must register new commands and drop old ones. Garry's Mod loadouts must survive death, respawn and a server restart.

    03

    Mods share one runtime

    Mods for one game come from different authors and often touch the same objects. When a target mod depends on others, it runs with them loaded: tasks pin third-party mods.

    04

    Real, varied ecosystems

    Twelve games, five languages (Lua and GLua, Java, C#, SourcePawn, Squirrel), several mod loaders, and both desktop games and dedicated servers.

    LIVE-RUNTIME HARNESS

    Four stages, all in the real game.
    A task is resolved only if every stage passes.

    1. 01

      Build

      Compile the submission with the game's own modding toolchain.

    2. 02

      Load

      Load it into the real game or its dedicated server, together with the pinned third-party mods.

    3. 03

      Test in game

      Run fail-to-pass and pass-to-pass scenarios inside the running game.

    4. 04

      Teardown

      End the session and check that it shuts down cleanly.

          PAPER

          GameSWE: Evaluating Coding Agents
          in Live Game Runtimes

          Anonymous submission · under review

          Abstract

          Coding agents are increasingly evaluated on repository-level tasks, where a change is judged by the repository's own tests. Yet much software runs inside a live host program, where correctness depends on runtime state, lifecycle events, and third-party components loaded alongside it. We introduce GameSWE, a benchmark of 150 repair and construction tasks built from open-source mods for 12 popular games across five programming languages. Each submission is compiled, loaded into the real game or its dedicated server together with the pinned third-party mods it depends on, and judged by fail-to-pass and pass-to-pass tests executed in the live runtime, without mocks or LLM judges. Across seven frontier and open-weight models, the best agent resolves 69.0% of tasks while three models remain at or below 25.0%, and even the best agent's per-game rate ranges from 40.0% to 93.3%. Our analysis shows that 70.0% of unresolved attempts end with the agent submitting its work as complete, and in at least 31.0% the agent reports that its own checks pass, yet the submission fails in the runtime, with failures concentrated at the boundary between code and host: interfaces the ecosystem does not provide, host conventions beyond the code, and logic not connected to the game's lifecycle. GameSWE provides a reproducible testbed for coding agents whose code must work where it runs.
